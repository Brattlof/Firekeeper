# Open questions about the Forever client

Blizzard has published no addon API notes for World of Warcraft: Forever. The client
reports interface `16001` (version 1.60.1) and pairs the modern UI architecture with a
vanilla game, so neither Classic Era habits nor retail habits can be assumed to hold.

Every question below is answered the same way: run the addon on the beta, type
`/fk caps`, and report what you see. A question closes when someone states the client
build they tested on and what actually happened.

Chat cannot be copied out of WoW, so the addon also writes its own answers down. At login
it records the client build and every capability probe into `FirekeeperDB.diagnostics`,
and the uncertain paths add to it as they run: whether the panel and the minimap button
drew, what index the camp channel joined on, and whether a waypoint was accepted. The
client flushes saved variables on `/reload`, logout or quit, so attaching
`WTF/Account/<account>/SavedVariables/Firekeeper.lua` answers most of the table without
anyone transcribing a line. It only ever writes that file — the beta never reads it back
(FK-9) — so it is a record of the session, not a setting.

| FK-2 | Does an upgraded campfire occupy an object slot, or replace the fire? | The planner currently assumes it replaces the fire, `Core/Plan.lua` | **Answered by the client's own tooltip.** Each campfire kit says it builds a fire "that allows cooking and the placement of up to N **additional** camp features" (Basic 3 / item 279981, Journeyman 5 / 279961, Expert 10 / 279974). Additional, so the fire is not one of the slots, which is what `Core/Plan.lua` already assumed. **Answered by the guides, not yet in game.** [classicwow.gg](https://classicwow.gg/forever/guides/camping) states the upgraded campfire is the fire itself with a larger capacity and is not counted as one of the slots, and every guide frames Basic/Journeyman/Expert as holding 3/5/10 objects. That is what `Core/Plan.lua` already assumes, so the assumption now has a source; placing one on a full basic fire would still confirm it. Place a cook's upgraded campfire on a full basic fire and count the slots |
| FK-3 | Can Legacy perk ranks be read from the API? | Ranks are typed in with `/fk legacy` today | Look for a Legacy namespace in the client's API and report it |
| FK-4 | May ordinary addons send addon messages, and in which channels? | Whether the group shares a plan or everyone plans alone | **Answered on 1.60.1.69913, from another addon's field notes.** `AreOutgoingAddonChatMessagesRestricted` returns true here even outside combat or an encounter (`diagnostics.outgoingRestricted = restricted=true`), but that is not a real block: [CooldownCollaborator](https://github.com/Nelnamara/CooldownCollaborator) found it "firing true far more often than expected... blocking every send before it was even attempted" and stopped consulting it. Firekeeper no longer gates on it either. Separately, that addon reports `SendAddonMessage` returning **nil** for success on this client although the declaration says the return is never nil, so `result ~= Enum.SendAddonMessageResult.Success` logged every good send as a failure; `Comm.WasSent` now accepts nil or 0. Prefix registration succeeds (`prefixRegistered = Success (0)`). Still open: a result code from a real send, which needs a group or a guild — a solo character records `firstSend = not sent: in no group, guild or raid`. **Open, and now instrumented.** On 1.60.1.69913 the `addonComm` probe says the API is there, but `addonCommOutgoing` says false. That single boolean cannot tell a realm restriction from a call that errored, so the addon now writes `diagnostics.outgoingRestricted` (the raw answer), `diagnostics.firstSend` (the result code of a real send) and `diagnostics.prefixRegistered`. `/fk caps` line `addonComm`, then `/fk plan` in a party of two. On 1.60.1.69913 the probe says yes; the party test is still open |
| FK-5 | Is a campsite's contents readable: slots used, objects placed, who placed them? | Today the camp is assembled from what players report to each other | **Answered on 1.60.1.69913: no such API.** The generated declarations for this build contain nothing for campsites; the only `Camp*` names are War Campaign and `PLAYER_CAMPING`, which is the vanilla "/camp to log out" event sitting between `LOGOUT_CANCEL` and `PLAYER_ENTERING_WORLD`. [S'more Skills](https://github.com/Henrik8210/smore-skills), the other camp addon for Forever, calls none either — its whole API surface is `C_Map`, `C_Timer`, `C_TradeSkillUI`, `C_Spell`, `C_SpellBook` and `C_NamePlate`. Players telling each other what they placed is therefore the established approach, not a workaround. Stand at a fire somebody else built and look for an API that describes it |
| FK-6 | Which UI templates exist (`BasicFrameTemplateWithInset`, `UIPanelButtonTemplate`)? | Panel styling, `UI/CampFrame.lua` falls back to a bare frame | **Also settled by not needing them:** the panel is drawn from plain textures and font strings as of `UI/Theme.lua`, uses no template at all, and `diagnostics.panel` records `drawn` on 1.60.1.69913. **Answered on 1.60.1.69913:** both exist. `/fk` draws the panel with its border and buttons, and both templates are defined in the Forever UI source (`Blizzard_UIPanelTemplates/Mainline/UIPanelTemplates.xml`, `Blizzard_SharedXML/Mainline/SharedUIPanelTemplates.xml`) |
| FK-7 | Do camp buffs and class buffs really overwrite rather than stack? | The whole point of the planner | Now with amounts: every buff is level-scaled across four to seven bands, e.g. the Incense Candle gives [2][6][12][18][25] Intellect. The exclusivity is named in each tooltip, and the Sharpening Wheel turns out to be **Strength / Strength of Earth Totem**, not Attack Power — that belongs to Mining's Lodestone, which is very likely what Blizzard's recap confused it with. **Answered by the guides.** Camp buffs are alternatives to class buffs, not additions: Incense Candle is exclusive with Arcane Intellect, Lodestone with Blessing of Might, and the First Aid Kit with Power Word: Fortitude. Blizzard describes the campsite stats as variants of buffs already tied to classes, meant to fill a gap rather than stack. The planner's whole premise therefore holds. Take Blessing of Might, then rest at a fire with a Sharpening Wheel, and watch the aura |
| FK-8 | Is the object cooldown one hour per player, per camp, or per object? | `Core/Cooldowns.lua` assumes one hour per player | **Answered by the client's own tooltip.** Every camp object ends with "All camping features share a cooldown of 1 hour" — so it is one hour per player across every camping feature, not per object and not per campsite, which is exactly what `Core/Cooldowns.lua` assumed. Place an object, then try a second one at another fire |
| FK-9 | Does the client read saved variables back? A community report says the beta writes them on exit but never loads them | Cooldowns, Legacy ranks and the debug flag survive a session only if it does, `Core/Init.lua` | **Answered on 1.60.1.69913: no.** After `/fk legacy fieldGuide 2` and two `/reload`s, the first write held rank 2 and the second was back to the default 0. BugGrabber's session counter also stayed at 1 across reloads. Saving works; loading does not Confirmed again across three sessions on 1.60.1.69913: `diagnostics.sessions` is a counter that climbs only if the file is read back, and it stays at 1. The addon now says so at login rather than letting a player think `/fk prof` was remembered, and the notice disappears by itself if a future build starts loading the file. |
| FK-10 | May an ordinary addon read auras on party members, and when do they come back secret? | Whether `/fk buffs` works and whether the planner trusts observed auras or guesses from class, `Core/Auras.lua` | **The combat half is answered, from a shipping addon's field notes.** [BuffWarden](https://github.com/vBaustad/BuffWarden) states that buffs cannot be read in combat on Forever, keeps its pre-pull state and updates when combat ends, and adds that during some encounters the game hides buffs outside combat too — so it shows nothing rather than guessing. It reads groupmates' auras as its core feature, which is the party half working outside combat. `Core/Auras.lua` already behaves this way: last good snapshot, marked stale, never an invented "nobody has it". **Partly answered on 1.60.1.69913:** `unitAuras` and `auraRead` both say yes, so an ordinary addon can read an aura outside combat; the probe reads the player's own. Still open: a party member's auras, and what comes back in combat. `/fk caps` lines `unitAuras` and `auraRead`, then `/fk buffs` in a party, in and out of combat |
| FK-11 | May an addon join a custom chat channel and send addon messages to it, and does this realm allow outgoing addon chat at all? | Whether `/fk find` can see strangers' camps, `Core/Discovery.lua` | **Partly answered on 1.60.1.69913:** joining works — a join call (now `JoinChannelByName`, `JoinPermanentChannel` at the time) put us on `FirekeeperCamps` and `GetChannelName` returned index 6 (`diagnostics.campChannel`). Sending is the open half: `addonCommOutgoing` came back false, which points at a realm restriction, but see FK-4. `/fk caps` lines `customChannel` and `addonCommOutgoing`, then `/fk host` on one character and `/fk find` on another |

| FK-14 | Can a camp object on the fire be recognised without the player typing `/fk place`? | Whether the camp fills itself in, `Core/Camp.lua` | Open. | FK-16 | Does a higher-tier object carry the lower tier's buff, so an Anvil makes a Sharpening Wheel a wasted slot? | Whether the planner may suggest two objects from one profession, `Core/Plan.lua` | **Answered by the client's own tooltips.** Every tier-2 and tier-3 object except Engineering's says it "provides all of the benefits of" its tier-1 object and "may be placed over" it to replace it. So an Anvil does carry the Sharpening Wheel's Strength, and the planner was indeed suggesting both. Fixed: `supersedes` in the data, `Data.EffectiveBuff` resolves it, and `Plan.EffectKey` keys a superseding object on the buff it ends up providing. Engineering is the exception — neither the Repair Bot nor the Anarchist's Workbench promises the lower tier. Open. A search summary claimed the Anvil "carries the Sharpening Wheel's buff and replaces it on the spot", but both guides checked directly say tier-2 and tier-3 effects are unreleased, so nothing was built on it. Place a Sharpening Wheel and an Anvil on the same fire and report whether the Strength or Attack Power aura appears once, twice, or not at all |
| FK-15 | Is the layer of a layered realm readable, and is `UnitGUID` secret in ordinary play? | Whether `/fk find` can say a camp is unreachable, `Core/Discovery.lua` | **Half answered on 1.60.1.69913.** `UnitGUID` came back readable in ordinary solo play outdoors — not secret — and the fifth field parsed as `12424` (`diagnostics.layer`). What is **not** established is that the number means "layer" in a way two players can compare. It is a GUID zoneUID, and the Classic layer trick assumes one value per shard; on a retail-based client a number that size may be per zone or per instance instead. `/fk find` therefore only calls a camp "on another layer" when it is on the same map as you, because across maps the numbers would differ anyway. To settle it: two characters in the same zone, `/fk find` on both, and compare `diagnostics.layer` — equal when together, different when one relogs onto another shard. `UnitGUID` is `SecretWhenUnitIdentityRestricted`, so it is tested with `issecretvalue` before being split. `diagnostics.layer` records the number or `not readable`: stand near any creature, type `/fk find`, then `/reload` |

| FK-17 | Where do the tier-2 and tier-3 Blueprints drop? | Whether `/fk train` can tell a player where to go, `Core/Route.lua` | **Narrowed, not answered.** Wowhead's Forever branch has the recipe but not its acquisition: `https://www.wowhead.com/forever/item=<id>&xml` returns a `createdBy` spell with its tier rank and full reagent list (the Anvil is spell 1263041, 5 Bronze Bar, 2 Coarse Grinding Stone, 2 Medium Leather, 10 sec cast), but there is no `droppedBy`, no vendor and no teaching item anywhere in the record. Research answers these faster than another `/reload` does, and most of the table was
settled without logging in. Two sources carry the weight:

**Wowhead's Forever branch has a JSON tooltip endpoint.** `https://nether.wowhead.com/forever/tooltip/item/<id>`
returns an item's name and its full rendered tooltip; the `/forever/` prefix is load-bearing,
and the same id without it is a 404. There is a matching `/forever/tooltip/spell/<id>`. This
is where the entire camp object table came from, and it is how a future object should be
checked before anyone is asked to look in game.

There is a second, older Wowhead endpoint that carries what the tooltip does not:
`https://www.wowhead.com/forever/item=<id>&xml` returns a `createdBy` block with the
crafting spell, its tier rank and every reagent. It has no drop or vendor data for these
items (FK-17), but it is the place to look for recipes.

**Other people's Forever addons** answered the addon-message result code (FK-4), the combat
aura behaviour (FK-10) and the absence of a campsite API (FK-5). Note that a search-engine
summary is not a source: two claims that arrived that way — the Anvil replacing the wheel,
and "an unlicensed addon publishes all 36 values" — turned out to be, respectively, absent
from the page it was attributed to, and a verbatim quote of this repository's own
`docs/DATA.md`. Fetch the page.

[docs/SOURCES.md](SOURCES.md) is the long version: what documentation exists for Forever
addon development, what does not, and which community dumps to look things up in. Read it
before adding a question here.

Two related pieces of community work are worth reading before adding to this list:
[ForeverTome's API handbook](https://github.com/Skold177/ForeverTome/tree/main/docs), which
catalogues restrictions and secret values in detail, and
[forever-bugs](https://github.com/ClassicWoWCommunity/forever-bugs) for client behaviour
in general.

## The rule this project follows

An API that has not been observed working on Forever is treated as absent. It gets a
probe in `Core/Capabilities.lua`, a fallback that still does something useful, and a row
in this table. No feature is allowed to depend on an assumption that has not been written
down here.
