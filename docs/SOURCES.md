# Blizzard documents nothing; Wowhead's JSON documents everything

There is **no Blizzard-published addon documentation, API change list, UI change note or patch note for World of Warcraft: Forever** — none on news.blizzard.com, none in the beta forums, and no blue reply to the forum thread that asks this exact question ([us.forums.blizzard.com thread 2348601](https://us.forums.blizzard.com/en/wow/t/wow-forever-addon-api-classic-retail-or-something-else/2348601)). The only Blizzard word of record on Forever's API is a single unattributed sentence relayed from the third-party WoW UI Discord — Forever "shares Mainline WoW's UI architecture, including the vast majority of APIs available in 12.1.5" ([Icy Veins](https://www.icy-veins.com/wow-forever/news/addons-in-wow-forever-blizzard-devs-just-addressed-the-big-question/)). What exists instead, and what an addon should actually code against, is a tier of community artifacts generated from the client itself: Ketho's `forever` branch of BlizzardInterfaceResources (build 1.60.1.69913, dumped 19 Sept 2026), the `forever` branch of Gethe's wow-ui-source carrying Blizzard's own generated API documentation with its restriction annotations, and warcraft.wiki.gg's per-function `Forever 1.60.1` availability badge. Against that backdrop, one late discovery changes the picture on the camping system entirely: **Wowhead's Forever branch exposes a working JSON tooltip endpoint at `https://nether.wowhead.com/forever/tooltip/item/<id>`, and all 36 campsite object IDs resolve through it with full rendered tooltips** — which converts the camping data from "36 names and effectively zero numbers" into a complete, primary-sourced table with exact buff amounts, named exclusivities, verified skill requirements and an explicit tier-replacement rule. It also settles the Sharpening Wheel dispute in favour of **Strength**, against Blizzard's own recap. The two questions that remain genuinely unanswered are whether addon messaging is restricted on Forever realms specifically (nobody has measured the flag on 1.60.1) and whether placed camp objects are reachable as units at all.

## Blizzard's entire Forever output is two panel recaps and a bug list

The official corpus is small enough to enumerate. The **Deep Dive Panel Recap** is the single most useful Blizzard document and the only one with camping mechanics: it states that "Placing a campfire creates a campsite where players can rest and gain access to useful benefits such as vendors, repairs, profession workspaces, and one-hour buffs", that "A Basic Campfire allows up to three special crafted objects to be added by nearby players", that "Each player can contribute one object, and those objects share a one-hour cooldown", and that Cooks "can learn upgraded Campfires that allow five or 10 objects to be placed at a camp" ([Blizzard News 24303313](https://news.blizzard.com/en-us/article/24303313/world-of-warcraft-forever-deep-dive-panel-recap)). The same article announces the realmless structure — "World of Warcraft: Forever is going realmless", four rulesets, "This is not one giant realm for everyone, and cross-ruleset grouping is not supported", two-part character names — and **never uses the words "layering" or "sharding"**. The **What's Next recap** mentions camping in one clause ([24303862](https://news.blizzard.com/en-us/article/24303862/world-of-warcraft-forever-whats-next-panel-recap)); the **beta-launch article** covers only installation and level cap ([24304160](https://news.blizzard.com/en-us/article/24304160/the-world-of-warcraft-forever-beta-now-live)). Kaivax's beta **Known Issues** post is the nearest thing to developer-facing Forever text and it is a bug list — Barber Chairs causing Lua errors, Legacy System hotkey Lua errors, Cooldown Manager implementation status — with **no client build number and no interface version given** ([forum thread 2352687](https://us.forums.blizzard.com/en/wow/t/wow-forever-beta-known-issues-september-18/2352687)). Not one official Blizzard source anywhere confirms version 1.60.1, interface 16001, the `wow_classic_beta` product, the `_classic_beta_` folder, or the "camelot" codename; every source carrying those identifiers is a datamine or a community dump.

The two substantial Blizzard addon articles both predate Forever and are explicitly scoped to Midnight. Ion Hazzikostas's **"Combat Philosophy and Addon Disarmament in Midnight"** is where the secret-value concept is stated in Blizzard's own words: combat state is "designated as a 'secret value' that can be displayed by addons, but not 'known' by them", and "Combat events are in a black box; addons can change the size or shape of the box, and they can paint it a different color, but what they can't do is look inside" ([24246290](https://news.blizzard.com/en-us/article/24246290/combat-philosophy-and-addon-disarmament-in-midnight)). The companion development-team article adds "Addons should not be able to automate combat decisions for the player" and carries a disclaimer that all of it "is subject to change" ([24244638](https://news.blizzard.com/en-us/article/24244638/how-midnights-upcoming-game-changes-will-impact-combat-addons)). **Neither mentions Forever, Classic, addon-to-addon messaging, or any specific restricted function.** The **UI Add-On Development Policy** is an unchanged 2009 document reposted in 2018, with eight clauses and no product scoping at all — free distribution, unobfuscated code, no negative effect on realm performance, no advertising, no in-game donation requests, ESRB "T" content, EULA compliance, and Blizzard's right to disable any addon functionality ([us.forums.blizzard.com thread 24534](https://us.forums.blizzard.com/en/wow/t/ui-add-on-development-policy/24534)). Nothing in it is newly relevant. The practical consequence is blunt: **an addon for Forever cannot cite Blizzard for any API guarantee**, and runtime capability probing is the only defensible source of truth — which is precisely what Firekeeper's `Core/Capabilities.lua` pattern already does.

## Ketho's `forever` branch, not a wiki, is the interface-16001 baseline

The community reference layer is well-built and only days old. **BlizzardInterfaceResources on its `forever` branch is the richest machine-readable Forever dump**, tip commit `1.60.1 (69913)` dated 19 Sept 2026, carrying `GlobalAPI.lua` (238,472 bytes), `Events.lua` (60,230), `LuaEnum.lua` (216,545), `CVars.lua` (205,135), plus `Templates.lua`, `Mixins.lua`, `WidgetAPI.lua` and `Frames.lua` ([Resources on forever](https://github.com/Ketho/BlizzardInterfaceResources/tree/forever/Resources)). Its README states the client identity outright — `GetBuildInfo() => "1.60.1", "69913", "Sep 17 2026", 16001`, with `WOW_PROJECT_ID => WOW_PROJECT_MAINLINE (1)` and `LE_EXPANSION_LEVEL_CURRENT => LE_EXPANSION_CLASSIC (0)` ([BIR forever README](https://github.com/Ketho/BlizzardInterfaceResources/blob/forever/README.md)) — which is the clearest single statement anywhere that Forever is a retail-family client running a level-60 game. **Ketho/WowDoc** carries the flavour under the internal name `camelot`: `Scribunto/API_info/patch/api/camelot/1.60.1.lua` is a flat name list of **6,866 global functions plus 189 Lua-standard names across 268 `C_*` namespaces**, tagged `-- version: 1.60.1 (69913)`, with no signatures, no events and no enums ([raw camelot/1.60.1.lua](https://raw.githubusercontent.com/Ketho/WowDoc/master/Scribunto/API_info/patch/api/camelot/1.60.1.lua)); WowDoc's own gametype table maps `camelot = "camelot", -- forever` into the `mainline` family alongside Midnight ([branches.lua](https://github.com/Ketho/WowDoc/blob/master/wowdoc/products/branches.lua)). That name list is what feeds **warcraft.wiki.gg**, whose per-function "Game Types" box shows a `Forever 1.60.1` row exactly when the function exists on 16001 — verified positive on [C_Secrets.ShouldAurasBeSecret](https://warcraft.wiki.gg/wiki/API_C_Secrets.ShouldAurasBeSecret) and negative on [UnitAura](https://warcraft.wiki.gg/wiki/API_UnitAura), which establishes the badge is real rather than decorative. **Signatures and Blizzard's own `SecureOnly`/restricted annotations live only in `Interface/AddOns/Blizzard_APIDocumentationGenerated/` on the `forever` branch of [Gethe/wow-ui-source](https://github.com/Gethe/wow-ui-source/tree/forever)** (mirrored as `forever-beta` on [BigWigsMods/WoWUI](https://github.com/BigWigsMods/WoWUI/tree/forever-beta), an independent extraction of the same drop six minutes apart). One trap in that tree: Forever's `.toc` files route "Camelot through mainline family UI plus Camelot overrides", so a file present on the branch may never be loaded — check the `.toc` routing before concluding a path is live ([ForeverTome implementation-client.md](https://github.com/Skold177/ForeverTome/blob/main/docs/implementation-client.md)). Ketho's **vscode-wow-api is unusable for Forever**: its flavour mask is four bits over live/classic/classic_anniversary/classic_era with no Forever bit and a generator that hardcodes those four branches ([Flavor.lua](https://github.com/Ketho/vscode-wow-api/blob/master/luasrc/ToTypeScript/Flavor.lua)).

Beneath the dumps sit first-week, single-author measurement repos whose value is that they tested an ordinary addon against a running client. **Thunderz96/forever-addon-kit** publishes a captured baseline of 6,045 globals, 11,417 named frames and 269 namespaces, and reports measured behaviours that matter: Classic globals such as `GetItemInfo`, `GetSpellInfo`, `UnitAura` and `CombatLogGetCurrentEventInfo` are gone; `C_Secrets`, `C_RestrictedActions` and a built-in `C_DamageMeter` are present; **`RegisterEvent` on an unknown event throws and aborts the file**; `ReloadUI()` is protected; error delivery stops after 100 Lua errors; and secure snippets cannot compile at all because `Blizzard_RestrictedAddOnEnvironment/RestrictedExecution.lua:22` captures a `loadstring_untainted` the client does not provide ([README](https://github.com/Thunderz96/forever-addon-kit/blob/main/README.md)) — independently confirmed by [GSE issue 2110](https://github.com/TimothyLuke/GSE-Advanced-Macro-Compiler/issues/2110). The same repo reports the beta game rule **`DisableCampsites=1`**, with what it gates unknown, while noting players are placing campfires anyway. **imperial64/forever-addon-dev** ships 6,577 generated signatures and 21 measured restrictions, including that registering `COMBAT_LOG_EVENT_UNFILTERED` is refused outright with `ADDON_ACTION_FORBIDDEN` even out of combat, and that `UnitPower` is secret at all times ([README](https://github.com/imperial64/forever-addon-dev/blob/main/README.md)). The best-established Forever client bug affecting addons is **saved variables being written to disk but never read back**, reported independently by forever-addon-kit, forever-addon-dev, an [EU forum thread](https://eu.forums.blizzard.com/en/wow/t/wow-forever-game-not-save-any-addons-settings/629470) and [forever-bugs issue 34](https://github.com/ClassicWoWCommunity/forever-bugs/issues/34) — four sources, which is as close to confirmed as anything in this corpus gets. Everything here was last touched between 18 and 19 Sept 2026 against a 4 Nov 2026 release, star counts are near zero, and the authors describe their own work as a "first-week snapshot". Treat it as evidence to re-verify, not documentation. Critically for a campsite addon, **there is no camping API on 16001**: grepping the whole camelot name list for `camp|Bonfire|Campfire` matches only `C_CampaignInfo.*`, `C_LoreText.RequestLoreTextForCampaignID` and `C_QuestLog.UpdateCampaignHeaders`, and the generated declarations for build 69913 contain nothing for campsites beyond a `PLAYER_CAMPING` event name.

## Wowhead's `nether.` JSON endpoint resolves all 36 objects and overturns Blizzard's recap

This supersedes the community-sourced camping picture. Wowhead's Forever branch renders item tooltips client-side, so a plain fetch of `wowhead.com/forever/item=<id>` returns the item name and nothing else — which is why every guide site and every prior research pass reported exact buff amounts as unobtainable. **The `nether.` subdomain defeats that**: `https://nether.wowhead.com/forever/tooltip/item/<id>` returns JSON containing the item name, quality, icon and the full rendered tooltip HTML. I verified it independently for this report: item 279944 returns `{"name":"Sharpening Wheel","quality":1,"icon":"inv_stone_grindingstone_01","tooltip":"…"}` with the complete use-effect text, and the branch prefix is load-bearing — the same ID without `/forever/` returns HTTP 404 ([nether.wowhead.com/forever/tooltip/item/279944](https://nether.wowhead.com/forever/tooltip/item/279944)). **All 36 campsite object IDs were fetched through it and every one resolved to the expected object name, so the ID list is fully verified.** The tooltip HTML also links the backing spell, which yields a second endpoint with more detail again: `tooltip/spell/1307392` gives the Sharpening Wheel's cast profile — **1 yd range, 10 sec cast, 1 hour cooldown** ([nether.wowhead.com/forever/tooltip/spell/1307392](https://nether.wowhead.com/forever/tooltip/spell/1307392)).

The single most consequential result: **the Sharpening Wheel grants Strength, not Attack Power.** Its tooltip reads verbatim, "Constructs a sharpening wheel that grants you and others sitting nearby [6][11][20][34] increased Strength, exclusive with Strength of Earth Totem" ([item 279944](https://nether.wowhead.com/forever/tooltip/item/279944)). Blizzard's Deep Dive recap says "Blacksmiths, for example, can place a Sharpening Wheel that increases Attack Power" ([24303313](https://news.blizzard.com/en-us/article/24303313/world-of-warcraft-forever-deep-dive-panel-recap)), and every guide site that asserts Attack Power — Warcraft Tavern, Icy Veins, lfcarry, MMOJUGG, BoostRoom, WoWSoD Pro — is restating that one recap sentence rather than reporting independently. Vote-counting made Attack Power look like the consensus; it was one source echoed seven times, and the client disagrees. The confusion has a tidy explanation the earlier research could not see: **Attack Power is Mining's buff**, delivered by the Lodestone, which grants "[12][20][32][49][67][90] increased melee Attack Power, exclusive with Blessing of Might" ([item 279960](https://nether.wowhead.com/forever/tooltip/item/279960)). Blizzard's recap appears to have attached the wrong profession's stat to its example. Two further disputes close at the same time. **Tier 2 and tier 3 objects do carry the tier-1 buff and do replace the lower object** — every one except Engineering's and Cooking's states "provides all of the benefits of" its tier-1 object and adds "May be placed over a [tier 1] to replace it", which is the explicit replacement mechanic no prior source could produce. And **the Faction Banner's exclusivity is Divine Spirit** — the gap earlier research correctly refused to guess at — with the banner split into faction-specific items whose text restricts the buff to "others members of the Alliance" (279973) or "of the Horde" (279972).

Several structural facts fall out of the table that no guide site had right. **The skill ladder 20 / 140 / 300 is now client-verified for every object**, because each tooltip carries its own `Requires <Profession> (<skill>)` line — which simultaneously verifies the profession assignment and kills the Fish Bowl dispute (the tooltip reads "Requires Fishing (20)", so it is Fishing tier 1, not Cooking). Item level tracks the tier exactly: **4 / 28 / 60** for tiers 1 / 2 / 3. Every one of the 36 ends with "**All camping features share a cooldown of 1 hour**" and a `(1 Hour Cooldown)` stamp with `Max Stack: 20`, which resolves Blizzard's ambiguous "those objects share a one-hour cooldown" as a **per-player cooldown across all camping features**, not per object type or per campsite. **The 36-object set is not 12 professions times three.** It is eleven professions times three, plus the Horde Faction Banner variant, plus Cooking's two — and it contains **no Campfire Kit at all**: Cooking's entries are Cookie's Feast and Iron Oven, which contradicts the widely copied guide-site claim that Cooking's three tiers are Basic / Journeyman / Expert Campfire Kit ([zockify](https://www.zockify.com/forever/camping-system/)). Cooking's two objects are also the only ones requiring "a Cooking Fire nearby" rather than "a Campfire nearby". Whether the upgraded 5- and 10-capacity campfires Blizzard describes exist as items outside this ID band is unresolved, and so is the related question of whether an upgraded campfire consumes an object slot.

Three gaps survive the endpoint and must be stated plainly. **The bracket notation is level scaling with no key.** `[6][11][20][34]` is a set of level-banded values rendered unresolved because the endpoint has no character context, and the band count varies per object — four for the Sharpening Wheel and Faction Banner, five for Incense Candle and Mana Well, six for Lodestone and First Aid Kit, seven for the Enchanted Lute's armor term. **Nothing states which player levels the bands attach to**, so exact values are now known while the mapping from level to value is not; the flat-value objects (Camp Chair's 2% crit, Fish Bowl's 8% stats, Camp Tent's 5% rested) do not scale at all. The **Enchanted Lute is unreadable as a clean data row**: its tooltip is a conditional template whose sentence structure itself varies by band — `[28][71][114][163][211][260][308] increase to Armor[][and][,][13][12][9][7][4][2][increase to all stats][, and 22][, and 16][, and 12][, and 6][increase to all resistances]` — so armor, all-stats and all-resistances terms cannot be separated confidently without an in-client reading. And **no source anywhere names a single blueprint's dungeon boss.** Blizzard says advanced campsite objects come from "advanced Blueprint recipes from dungeon bosses" and names no boss; Icy Veins lists "Every advanced Blueprint recipe and its dungeon boss source" as unknown ([Icy Veins camping](https://www.icy-veins.com/wow-forever/camping)). The tooltips are silent on acquisition. Item level 28 and 60 for tiers 2 and 3 is the only new hint, and it is a hint about content tier, not a source. Blueprint sources remain the largest unfilled column in the object table, and the tooltip endpoint cannot fill it — that needs the Wowhead item page's drop-source section or an in-game sighting.

## No Forever measurement of the messaging flag exists; the return code is the only honest gate

`C_ChatInfo.AreOutgoingAddonChatMessagesRestricted()` is **not** an encounter lockdown flag. Blizzard's generated documentation on the `forever` branch describes it verbatim as a realm-level switch — "Returns false if addons are allowed to send outgoing chat messages. This is controlled on a realm-by-realm basis (tournament realms allow it), and the ability for addons to receive comms is controlled separately" — text identical to the `live` branch, with no `SecretArguments` and no `HasRestrictions` field ([forever ChatInfoDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/ChatInfoDocumentation.lua)). Blizzard's own UI uses it once, as a module load gate: `if not C_ChatInfo.AreOutgoingAddonChatMessagesRestricted() then CooldownBroadcaster_LoadUI(); end` ([EventImplementation.lua](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_Game/Mainline/EventImplementation.lua)). Two independent retail-12.0 authors report it reading `true` on ordinary realms outside any encounter and abandoned it: CooldownCollaborator's comment records that it "was firing true far more often than expected (outside any encounter or death window), blocking every send before it was even attempted", and that `SendAddonMessage`'s return code "is the authoritative signal" ([Comms.lua](https://github.com/Nelnamara/CooldownCollaborator/blob/main/Comms.lua)); Lodestar bakes the same observation into a test stub ([wowstub.lua](https://github.com/Co2Noss/Lodestar/blob/main/.dev/wowstub.lua)). BigWigs never calls it. **Both of those are retail addons, not Forever addons — and no one has recorded what the function returns on a Forever beta realm.** That is the central unanswered question of this brief, and the honest answer is that the Forever realm switch's state is unmeasured.

On the return value, the declaration and the field disagree, and the field wins. Forever's declaration says `{ Name = "result", Type = "SendAddonMessageResult", Nilable = false }` — while the sibling `SendAddonMessageLogged` on the same Forever file declares the same field `Nilable = true`, so Blizzard's generated docs contradict themselves about nilability ([forever ChatInfoDocumentation.lua](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/ChatInfoDocumentation.lua)). Shipping addons assume non-numeric returns are possible: BigWigs guards with `if type(result) == "number" and result > 0 then` at three call sites ([BossPrototype.lua](https://github.com/BigWigsMods/BigWigs/blob/master/Core/BossPrototype.lua)), and the Forever addon `smore-skills` treats only `false` as failure ([Sync.lua](https://github.com/Henrik8210/smore-skills/blob/main/SmoreSkills/Sync.lua)). **The defensible contract is: success iff the result is `nil` or `0`; retry on 3 (AddonMessageThrottle), 8 (ChannelThrottle) and 9 (GeneralError); give up silently on 11 (AddOnMessageLockdown); report anything else** — the full enum runs 0 Success through 12 TargetOffline, with 11 added in 11.1.0 and 12 in 12.0.0 ([Enum.SendAddonMessageResult](https://warcraft.wiki.gg/wiki/Enum.SendAddonMessageResult)). Limits are unchanged at a 16-character prefix and a 255-byte message, with a 10-message per-prefix allowance ([API C_ChatInfo.SendAddonMessage](https://warcraft.wiki.gg/wiki/API_C_ChatInfo.SendAddonMessage)); the refill rate has no primary source, and ChatThrottleLib's 800 CPS and 4000-byte burst are its own documented guesses, not Blizzard figures. One Forever-specific hardening is visible in the declarations: `SendAddonMessage` carries `SecretArguments = "NotAllowed"` on the `forever` and `live` branches but has no such field on the `classic_beta` branch — concrete evidence that Forever's chat API is generated from the Mainline code path.

There are **three independent gates** here, and conflating them is what produced the "the flag is useless" reports. The realm-level switch is one. The **content-scoped lockdown** is another: the 12.0.0 rule began as "The ability to send addon messages and read chat is currently restricted entirely while inside an instance" and was relaxed during alpha to apply only while a Mythic+ run, a PvP match or an instance encounter is in progress ([Patch 12.0.0/Planned API changes](https://warcraft.wiki.gg/wiki/Patch_12.0.0/Planned_API_changes)) — which makes it largely irrelevant to an open-world campsite addon, and which flatly contradicts the commercial-site claims that raid addon comms are banned outright. The third gate, and the one that actually bites on Forever, is **taint**. The only Forever addon doing cross-player comms records that the client "pops *SmoreSkills has been blocked from an action only available to the Blizzard UI*" if it calls `JoinPermanentChannel` or `JoinChannelByName` from login, zoning or a timer, or `SendChatMessage`/`SendAddonMessage` from `UNIT_SPELLCAST`, the combat log, `C_Timer` or `OnUpdate`; its working rule is that joins and sends happen only from a hardware event — a button click or a slash command ([smore-skills FOREVER.md](https://github.com/Henrik8210/smore-skills/blob/main/FOREVER.md)). That rules out periodic heartbeats. Its transport is a hidden named channel joined on click plus addon whisper, with `JoinChannelByName` preferred because `JoinPermanentChannel` sticks in chat config and can steal `/1` ([Sync.lua](https://github.com/Henrik8210/smore-skills/blob/main/SmoreSkills/Sync.lua)). The honest caveat that author records is decisive: **two-client delivery over that channel was never confirmed before the beta servers went down.** So on Forever, sends are proven not to error after a click; end-to-end delivery is not proven at all.

## A zoneUID names a zone instance, and camp objects are almost certainly not units

The GUID field everyone calls "the layer" is real but misnamed. The 6.0.2+ format is `Creature-0-[serverID]-[instanceID]-[zoneUID]-[ID]-[spawnUID]`, and `GameObject`, `Vehicle` and `Pet` share that shape exactly, while `Player-[serverID]-[playerUID]` has **no zoneUID field at all** — so no layer read can come off a player GUID ([Warcraft Wiki: GUID](https://warcraft.wiki.gg/wiki/GUID)). Splitting on `-` yields seven tokens and the fifth is `zoneUID`. Both mainstream implementations read that token: NovaWorldBuffs parses `unitType, _, _, _, zoneID, npcID, spawnUID = strsplit("-", GUID)` ([NovaWorldBuffs.lua](https://github.com/hippuli/NovaWorldBuffs/blob/master/NovaWorldBuffs.lua)) and SilverDragon, a maintained retail addon, names the function `addon:GUIDShard` ([util.lua](https://github.com/kemayo/wow-silverdragon/blob/master/util.lua)). **But a zoneUID identifies one instantiation of one zone, not a realm-wide layer.** NovaWorldBuffs has to anchor "Layer 1 / Layer 2" to a capital city's zoneUID, maintain a per-layer `zoneUID -> uiMapID` map, and apply a numeric-proximity sanity check with `offsetLimit = 999` for Classic and `200` otherwise, precisely because the value differs for every zone on the same layer; the user-facing layer number is the sort position of known capital-city zoneUIDs, not anything in the GUID. Observed magnitudes run from three digits to six (Blasted Lands 814, Feralas 966, Mulgore 12138, Azshara 128144), with the author's note that "Legit layers can appear with higher than 10,000 zoneid if created later in the week" — the signature of a monotonic server-side counter of zone-instance creations. **The direct consequence: comparing two players' zoneUIDs is valid only within one zone**, which is exactly the constraint Firekeeper already enforces by comparing layers only when the camp is on your map. Forever's own ground truth fits the pattern — on build 1.60.1.69913 `UnitGUID` came back readable in ordinary solo play outdoors and the fifth field parsed as `12424` (`C:\Users\palle\Dev\Firekeeper\docs\RESEARCH.md`, row FK-15), a five-digit counter value, not a small layer index.

Two things make this worse on a 12.0-era client. First, Forever is **per-zone sharded, not layered**: beta players report the five-minute world-refresh warning three times inside a single levelling zone, involuntary phasing mid-combat, general chat cut off by refreshes, and players popping in and out at zone borders, with one player summarising that Blizzard "stated a few times that this is per-zone. So it is essentially 'sharding'" — and **no Blizzard reply anywhere in the thread** ([us.forums.blizzard.com thread 2353028](https://us.forums.blizzard.com/en/wow/t/shardinglayering-too-common/2353028)). Forever's forum tracker also carries "Forming or leaving a party sometimes immediately layers you without warning" ([forever-bugs issue 33](https://github.com/ClassicWoWCommunity/forever-bugs/issues/33)). A shard that refreshes on a timer gives a zoneUID a useful lifetime of minutes. Second, **`UnitGUID` can return a secret value on 12.0**, in which case it cannot be compared or used as a table key; the triggering predicate `SecretWhenUnitIdentityRestricted` fires "when the unit isn't player-controlled or in party/raid", which describes every world creature and every placed camp object ([Warcraft Wiki: Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values)). Real breakage is already logged — TipTac errors with "attempt to compare local '_unitGUID' (a secret string value)" on a mouseover ([TipTac 491](https://github.com/frozn/TipTac/issues/491)) — and SilverDragon's shard reader now opens with `if issecretvalue(guid) then return end`. Nothing documents whether `strsplit` on a secret string succeeds, errors, or yields secret substrings, so guarding before the split is the only safe pattern. **There is no supported layer or shard API on any modern flavour**: the wiki's Layering page documents no detection method, and standing player requests for a shard-ID addon have no working answer. The only honest output for an addon is a tri-state — same zone instance, different zone instance, or unknown — never a layer number.

On the last question, **placed campsite objects are GameObjects, not units, with two probable exceptions.** GameObjects do have GUIDs in the Creature shape and therefore do carry a zoneUID, which is why accepting a `GameObject-` prefix in a layer read is right in principle. But the only first-class handle on a GameObject in the API is the `softinteract` unit token, which since Patch 10.0 "may be an NPC such as a questgiver or merchant, **or a game object like a mailbox or a gathering node**" ([Warcraft Wiki: UnitId](https://warcraft.wiki.gg/wiki/UnitId)); it is singular, gives one soft-targeted object rather than a list, and **what `UnitName`, `UnitGUID` and `UnitExists` return for such a token is documented nowhere**. Nothing suggests GameObjects get nameplates, so `C_NamePlate.GetNamePlates()` should see none of them — and there has never been an API to enumerate nearby world objects on any modern flavour. The exceptions are Engineering's two bots. Both are **summoned** and both act as vendors — "Summons a Reagent Bot that allows you and others nearby to purchase reagents" (279950) and "Summons a Repair Bot that allows you and others nearby to buy reagents and repair gear" (279949) — a merchant window requires a merchant, the Repair Bot's icon is `INV_RobotPet`, and the vanilla precedent is an NPC with an ID (Field Repair Bot 74A, [NPC 14337](https://www.wowhead.com/classic/npc=14337/field-repair-bot-74a)). If they are Creatures they would have nameplates and resolvable `UnitGUID`, making a Reagent Bot the most reliable layer source at a camp. The verb alone is not the tell, though: the Enchanted Lute is also "Summons" and is a lute. The full tooltip set makes the split visible — everything else uses object-placement verbs ("Constructs", "Places", "Erects", "Unrolls", "Assembles", "Builds", "Ignites", "Lay out"), so at most **2 of 36 objects** are plausibly units, which is not a foundation for auto-detecting camp contents. Combined with the enumeration gap and the secret-value rules, there is no path to reading a campsite's contents on this client; players telling each other what they placed is the only mechanism.

## Conclusion

The documentation picture inverts the usual hierarchy. For Forever, Blizzard's published word is the *weakest* source available — it is marketing prose, it names no build, and on the one camping detail that can be checked against the client it is **wrong** about which stat the Sharpening Wheel grants. The authoritative sources are all machine extractions of the client: Ketho's `forever` branch for existence, wow-ui-source's `forever` generated documentation for signatures and restriction flags, and now Wowhead's `nether.` JSON tooltip endpoint for game data. That last one deserves to be treated as infrastructure rather than a one-off: it turned the camping table from four Blizzard-sourced effects and zero verified amounts into 36 verified IDs with exact values, named exclusivities, client-verified skill requirements and an explicit replacement rule, in a single pass — and the spell-tooltip variant it links to adds cast time, range and cooldown. Any repository policy that says buff numbers cannot be sourced without an in-game sighting should be revised to admit this endpoint, with the standing caveat that a beta database is a moving target and the bracket-to-level mapping is still missing.

What that leaves is a short, sharply defined list of things only the client can answer, and all of them are behavioural rather than data. Whether Forever's realm switch restricts outgoing addon messages is unmeasured on 1.60.1 by anyone; whether a channel message actually reaches a second Forever client has never been confirmed; whether `UnitGUID` is readable for a placed camp object, and whether `strsplit` survives a secret string, are undocumented in principle rather than merely unfound. Those are exactly the questions a capability probe answers and a research table records, and the reason to keep the probes is not caution — it is that for these four items there is no document in the world to read instead. Meanwhile the most valuable supported signal on Forever is probably not a layer ID at all but the five-minute world-refresh warning: whatever event carries it marks the moment every cached camp position becomes suspect, which is more actionable than any number parsed out of a GUID.
